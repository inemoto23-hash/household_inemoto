## 1. やったこと

同じ「イオン」を2店舗で使うと店名で束ねられ、金額が合算されてピンも1つになる。
**店の実体を持つ台帳（`dbo.places`）を作り、`entries.place_id` が指す形にした。**

### 束ねる鍵は座標のかたまり。地名は表示のための飾り

町境の近くの店は GPS のばらつきで訪問ごとに町名が変わりうる。
「店名＋地名」を鍵にすると同じ店が2つに割れるので、鍵にしない。

| 記録の状態 | どうするか |
|---|---|
| 座標がある | 同名のマスタのうち **200m 以内でいちばん近いもの**。無ければ新しく作る |
| 座標がある・同名のマスタが座標なし1件だけ | そのマスタに座標を書き込んで**育てる** |
| 座標が無い・同名のマスタが1件 | それを指す |
| 座標が無い・同名のマスタが複数 | **紐付けない** |
| 座標が無い・マスタも無い | **作らない** |

**「育てる」を入れたのが要。** 一括登録しか無かった店に初めて現地から記録したとき、
新規作成にすると同じ店が2つに割れ、片方に一括登録ぶん、もう片方に現地ぶんが溜まる。

**当てずっぽうに選ばない。** 座標が無く同名が複数あるときは紐付けない。
選ぶと金額が別の店に混ざり、後から気付けない。

### 地名は国土地理院から取る

Azure Maps の POI・逆ジオは日本ではローマ字しか返さず不採用にしていたが、
**国土地理院は行政地名そのものが本業**なので日本語で正しく返る。しかも **API キーが不要**で、
「接続文字列とAPIキーをどこにも保持しない」という方針を崩さずに済んだ。

```
GET https://mreversegeocoder.gsi.go.jp/reverse-geocoder/LonLatToAddress?lat=&lon=
→ {"results":{"muniCd":"11216","lv01Nm":"東六丁目"}}
muniCd 11216 = 埼玉県 羽生市
```

コード→名前の変換表（`domain/muni.ts`、1,919件）は `muni.js` からの**生成物**。
実行時に取りに行かない。市区町村コードは合併でしか変わらないので、
黙って壊れるより手作業で気付ける形にした。

### 地名は定時ジョブが埋める（記録の保存では呼ばない）

`placeGeocodeSweep`（15分ごと、1回20件、間隔400ms、失敗3回で打ち切り）。

保存を外部 API の応答待ちにすると、あちらが遅い日は記帳が遅くなり、
止まっている日は記帳できなくなる。**地名は飾りなので、それと引き換えにしない。**

国土地理院は地理院地図向けの提供で **SLA が無い**。一度書いたら二度と引かないので、
止まっても既存のマスタは動き続け、新しい店に地名が付かなくなるだけで済む。

### 記録に書く店名は利用者の呼び方のまま

`display_name`（「セキ（鴻巣市）」）は**マスタ側の計算列**で、表示にだけ使う。
記録の `merchant` に地名まで書き込むと、地名の付き方が変わったときに
過去の記録だけ古い名前で残る。店名候補は `name`（入力欄用）と `label`（見出し用）を分けて返す。

## 3. 判明したこと

**座標を持つマスタが 45件中3件しか無い。** 支出マップにピンが3本しか出ないのはこれが理由。
一括登録・自宅での記録・誤差500m超の切り捨てで、ほとんどの記録が座標を持たない。

同名の別店舗の問題は**まだ実害として現れていない**（マスタが1店舗ずつ）。
今回入れたのは、今後そうなったときに割れないようにする仕組み。
