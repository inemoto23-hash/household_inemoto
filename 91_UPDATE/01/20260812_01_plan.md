# リストからの一括登録（/bulk）

## Context

いまの記帳は「カレンダーで日付を選ぶ → シートで明細を1件入力 → 保存」の1件ずつの導線しかない
（`system_flow.md` の「記帳」）。レシートの束やカード明細をまとめて打つときは、
1件ごとにシートを開き閉じすることになり、同じ日付・同じ口座を何度も選び直すことになる。
「続けて入力」チェックはあるが、入力済みの行を見比べながら直すことはできない。

そこで、行を積み上げて**一度に登録する画面**を追加する。1行の項目は
種別（既定=支出）/ 金額 / 日付 / カテゴリ / 口座 / 店先・支払名。

### 合意済みの前提（Q&A で確定）

1. 新規ページ `/bulk`。カレンダー上部のボタン列に「📋 まとめて」を足して遷移する
2. 種別は **expense / income / refund のみ**。振替は対象外（移動元・移動先で列の意味が変わるため）
3. カテゴリ欄は「予算カテゴリ」と「プール」を2グループに分けた**1つの選択欄**
4. **部分失敗は認めない。** サーバーが全行を検証し、1行でも不備があれば何も登録せず、
   何行目の何が問題かを返す。書き込みは1トランザクション

## 設計の要点

### 「全か無か」は、書き込みの前に検証を終わらせることで作る

検証（zod → `normalizeEntry` → 参照IDの世帯チェック）を**全行分やり切ってから**
`transaction.begin()` する。通常の不備では1行も INSERT されない。
万一 DB 制約（`ck_entries_shape` / FK）が発火しても1トランザクションなので全部戻る。

### 負担先は1つの文字列で持つ（`chargeKey`）

`EntryForm` は `chargeTo` + `budgetCategoryId` + `poolId` の3つで負担先を表しているが、
一括では `chargeKey: 'c:12'` / `'p:3'` の**1文字列**にする。
「カテゴリとプールの両方が入っている」状態を構造的に作れなくなる。
選択肢を作る時点で排他になるので、収入のときはプール群がそもそも出ない。

### 位置情報は受け取らない

一括入力はレシートの束を後から打つ用途で、入力者はその場にいない。
現在地を付けると全行に無関係な座標が入り、支出マップと店名候補を汚す。
`stripIfAtHome` は「自宅なら捨てる」だけなので、外出先で打つと座標が残ってしまう。
**入口で受け取らない**（zod に項目を置かない）。画面が送ってきても消える。

### 参照IDの検証は行数によらず往復1回

既存 `assertReferencesInHousehold` は1件につき最大3往復。50行なら150往復で Basic 5DTU では持たない。
全行から カテゴリ / 口座 / プール の ID 集合を作り、**1リクエストに3つの SELECT を並べて
`recordsets` で受ける**（`calendarMonth` と同じ書き方）。既存の単件版はそのまま残す。

## BE

### 新エンドポイント

`POST /api/entries/bulk` — 関数名 `entriesBulkCreate`、新規ファイル
[entriesBulk.ts](11_BE_DEPLOYMENT/src/functions/entriesBulk.ts)。
`entries.ts` は既に507行あるので追記しない。`entries/{id}` は PATCH/DELETE のみなのでルート衝突しない。
[index.ts](11_BE_DEPLOYMENT/src/index.ts) に import を足す（足し忘れると 404）。

### [domain/entry.ts](11_BE_DEPLOYMENT/src/domain/entry.ts) に追加

- `BULK_ENTRY_KINDS = ['expense','income','refund']`
- `bulkEntryRowSchema` — 既存 `entryInputSchema` から `lat/lng/locationAccuracy/placeName/clientId/counterAccountId` を `.omit()` し、`kind` を3種別に絞る
- `bulkEntryInputSchema` — `{ clientId?, rows: array(...).min(1).max(50) }`
- `MAX_BULK_ROWS = 50`（パラメータ数 11×50=550。mssql の上限2100に余裕）
- `NormalizeResult` に **optional** な `field?: 'amount'|'accountId'|'budgetCategoryId'|'poolId'` を追加し、
  各エラー分岐で埋める。optional なので既存の呼び出し元2箇所は無変更で通る。
  これで画面がセル単位で赤くできる

### 処理順

```
zod → 全行 normalizeEntry（1件目で止めず全部集める）
    → 参照ID の一括検証（往復1回）
    → 不備が1件でもあれば 400。ここまでトランザクションを開かない
    → begin → clientId 重複チェック → 多値 INSERT（1文）→ commit
```

INSERT は `VALUES (@d0,@k0,...),(@d1,@k1,...)` の1文にまとめる。
`counter_account_id` / `lat` / `lng` / `location_accuracy` / `place_name` / `source` は
**列ごと書かない**（NULL と `DEFAULT N'manual'` が入る）。
`source` は `'manual'` のまま。`ck_entries_source` に `'bulk'` を足すには migration が要るうえ、
一括も人が手で打ったものなので由来は同じ。

### 冪等性

**バッチ全体に UUID を1つ。** 画面が送信時に採番し、成功するまで再送に同じ値を使う。
サーバーはトランザクション内で `client_id` の存在を1回引き、あれば何も書かず 200 を返す。
保存は**先頭行にだけ**その値を入れる — `ux_entries_client_id (household_id, client_id)` が
部分ユニーク索引なので、全行に同じ値を入れると2行目で違反する。
「client_id はバッチの受付番号で、先頭行に刻む」とコメントで明示する。
すり抜けた同時押しは索引が最終防衛線になる（2601/2627 → 409 `DUPLICATE_BATCH`）。

### エラーの形

```
400 VALIDATION_ERROR
{ error: { code, message: '3 件の行に不備があります',
  details: { rows: [ { index: 0, field: 'amount', message: '金額は1円以上で入力してください' }, ... ] } } }
```
`index` は送った `rows` の0始まり添字。`message` は日本語のままで、画面はそのまま出せる
（画面側にコード→文言の対応表を持たせない）。
行に紐付かない不備（行数0、51行以上、JSON壊れ）は `details.rows` を持たない。

成功は `{ data: { created: 12, ids: [...] } }`（201）。登録した明細そのものは返さない —
画面は React Query を invalidate して取り直すため。

### 既存挙動に合わせること

締め済み月のチェックとプール残高チェックは**しない**。既存 `entriesCreate` がしていないため、
ここだけ厳しくすると経路で挙動が割れる。

## FE

### 行の状態型（`EntryFormValue` は使わない）

```
interface BulkRow {
  key: string;        // 配列 index を React key にすると行削除で入力が1つずれる
  kind: 'expense' | 'income' | 'refund';
  amount: string;
  entryDate: string;
  chargeKey: string;  // 'c:12' | 'p:3' | ''
  accountId: string;
  merchant: string;
}
```

`EntryFormValue` は transfer / payVia / transferMode / recurrence を抱えていて一括には重く、
負担先の持ち方も違う。ダミーを詰めて `toPayload` を呼ぶと読み手が止まる。
**共通の真実はサーバーに送る JSON の形だけ**にし、状態型は画面ごとに持つ。この線引きをコメントに書く。

`payVia`（財布/クレジット）も持たせない。全口座を1つの選択欄にグループ分けで出す。
一括はカード明細をまとめて打つ用途が主で、絞り込みを1タップ挟まないほうが速い。

### 選択肢の組み立てを共通化する（SSOT）

`accountGroups()` と `categoryItem()` は [EntryForm.tsx](10_SITE_DEPLOYMENT/src/features/entries/EntryForm.tsx) の非 export。
口座の並べ方（優先→種別ごと）とクレジットの見せ方（正で「支払」）が2箇所に分かれると、いずれ片方だけ直る。
→ 新規 `features/entries/pickOptions.ts` へ移設して export し、`EntryForm` は import に差し替える
（**振る舞いは1ミリも変えない**）。ここに `chargeGroups(categories, pools, kind)` を足す。

### セル用の選択部品

[PickField.tsx](10_SITE_DEPLOYMENT/src/components/PickField.tsx) はラベルが縦積みで出て `min-height:46px`、
しかも開くとインラインで下に伸びるため、表のセルに置くと行の高さが変わって下が押し下げられる。

→ `PickField` の中のリスト部分を **`PickList` として切り出して export**（DOM と見た目は完全に据え置き）。
新規 `components/PickCell.tsx` はラベルなし・40px で、押すと既存 `Sheet` を開いて中に `PickList` を出す。
`aria-label` を props で受け、可視ラベルなしでも読み上げが成立するようにする。

### PC の表 / スマホのカードは CSS だけで書き分ける

**DOM は1つ。** `.bulk-*` クラスでレイアウトだけ切り替える。区切りは既存 `.sheet` と同じ **900px**。

- `~899px` — カード。金額と日付を2列、残りは全幅。セル内ラベルを表示
- `900px~` — 表。`grid-template-columns: 72px 100px 118px minmax(0,1.3fr) minmax(0,1.1fr) minmax(0,1.2fr) 56px`、
  セル内ラベルは `display:none`、列見出しを上に1回だけ出す。`.tx-row` と同じく下線で区切る

不備行は `[data-invalid='true']` に `inset 3px 0 0 var(--expense)`、セルは `aria-invalid` に outline。

> `.app-shell` は `max-width:760px`。7列は窮屈なので、まず760px内に収めて実装し実機で見る。
> 厳しければ `/bulk` のときだけ `<main>` に別クラスを足して広げる（画面ごとに幅が違う状態は
> 統一感を損なうので、必要になってから）。

### 行の操作

- **追加** — 直前の行の 日付 / 口座 / 種別 を引き継ぎ、金額・店名・カテゴリは空
  （同じ日のレシートはカテゴリが変わることが多い）
- **複製（⧉）** — カテゴリと店名まで丸ごとコピー（同じ店で金額違いを続けて打つとき）
- **削除（×）** — 即時。入力済みの行を消したときだけ `CalendarPage` の `undoTarget` と同じトーストで戻せる
- 1行のときは削除を disabled、50行で追加を disabled にし理由を横に書く
- 補助として「全行の日付を揃える」欄をヘッダーに置く

### 送信前の検証と、サーバーの details の紐付け

- `rowIssue(row)` はサーバーの `normalizeEntry` と同じ条件を先に画面で見る（既存 `canSubmit` と同じ位置づけ）
- **完全に空の行は送信対象から自動で外す**が、「空の行 n 件は登録しません」と必ず書く。黙って捨てない
- 送信ボタンが無効なときは理由を書く（「あと2行に不備があります」）。押した時点で最初の不備行へスクロール
- 送信時に `sent[i].key` の配列を保持し、400 の `details.rows[].index` から行の key に戻して
  `Map<rowKey, issue>` に置く。その行を編集した瞬間に表示を消す（直ったか分かるように）
- `details` が想定の形でないとき（500・ネットワーク・旧デプロイ）は従来どおり上部の `ErrorText` に落とす。
  **必ず両方の道を用意する**

### 成功後

`['calendar'] ['entries'] ['bootstrap'] ['budgets'] ['analytics']` を invalidate（前方一致なので月キーは不要）。
画面には留まり、上部に「12件を登録しました」＋「カレンダーで見る」を出して行を空1行に戻す。
続けて打ちたい場面が多いので自動で戻らない。

## 懸念点

1. **760px に7列**（最大の実装リスク）。詰めて実装し、実機で厳しければ `/bulk` だけシェルを広げる
2. **`PickField` に手を入れる** — 既存6画面が使う部品。`PickList` 切り出しは DOM も見た目も変えない、を厳守し、
   直後に既存画面を確認する。完全に独立実装すれば既存に触らずに済むが、選択肢の並べ方が2箇所に分かれる
3. **全か無かの代償** — 50行のうち1行が悪いと49行も入らない。合意事項なので変えないが、
   その分「どの行がなぜ駄目か」を確実に返せないと使い物にならない。**details の行番号紐付けがこの機能の要**
4. **バッチ clientId を先頭行にだけ入れる非対称さ** — 索引を足さずに二重登録を防げる代わりに説明が要る。
   将来 `entry_batches` を作れば綺麗になるが、現規模では過剰
5. **`BulkRow` と `EntryFormValue` の二重管理** — 線引きをコメントに明記しないと
   「共通化されていない」と誤解される
6. **一括で入れたものは支出マップに出ず、店名候補の学習にも効かない**（位置情報なしのため）。
   まとめて打つ用途では正しい
