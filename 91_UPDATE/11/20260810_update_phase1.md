# 20260810 アップデート予定（Phase 1）

- **計画書**: [91_UPDATE/01/20260810_rebuild_plan.md](../01/20260810_rebuild_plan.md)
- **区分**: Phase 1 — 中核（口座・カテゴリ管理、取引CRUD、カレンダー、その場編集）

## 完了条件

**現行アプリと同等の記帳ができる。ただし編集で画面遷移しない。**
これを満たした時点で現行アプリ（Railway）から乗り換え可能とする。

## 設計上の要点

### 1. 画面遷移で状態を失わせない

現行アプリ最大の不満（修正のたび入力画面に飛ばされる）への回答。

| 施策 | 内容 |
|---|---|
| その場で編集 | モバイル: ボトムシート / PC: 右インスペクタ。一覧は開いたまま |
| 楽観的更新 | 保存押下で即座に一覧へ反映。失敗時のみロールバックして通知 |
| URL に状態を持つ | `/calendar/2026-08?d=12&e=4821`。リロード・戻る・共有で復元 |
| 連続入力 | 保存後もシートを閉じず、金額だけクリアして次の1件へ |
| Undo | 削除は論理削除 + トーストから復元 |

### 2. 種別ごとの入力項目はサーバーが担保する

`ck_entries_shape` により不整合レコードは DB が拒否する。
フロントの手動クリア処理（現行の `toggleExpenseCategory()` 相当）には依存しない。

### 3. 金額は `BIGINT` 円単位整数

`db/convert.ts` を通して API 境界で必ず `number` へ正規化する。

## 実施内容

### バックエンド

| エンドポイント | 用途 |
|---|---|
| `GET /api/bootstrap` | 初回一括取得（世帯・利用者・口座・カテゴリ・プール・当月サマリ） |
| `GET /api/entries` | 期間・カテゴリ・口座・キーワードで検索 |
| `POST /api/entries` | 登録（`client_id` による冪等性） |
| `PATCH /api/entries/{id}` | 部分更新。種別変更時の項目整合はサーバーが担保 |
| `DELETE /api/entries/{id}` | 論理削除 |
| `POST /api/entries/{id}/restore` | Undo |
| `GET /api/calendar/{ym}` | 日別集計（収支・件数） |
| `GET /api/categories` | カテゴリ一覧 |
| `POST/PATCH/DELETE /api/categories[/{id}]` | カテゴリ管理（並び替え含む） |
| `POST/PATCH/DELETE /api/accounts[/{id}]` | 口座管理（並び替え含む） |

### フロントエンド

- アプリシェル（モバイル: ボトムナビ / PC: サイドレール + 3ペイン）
- カレンダー画面（月グリッド + 日別収支 + 日別リスト）
- 取引編集シート（新規・編集・複製・削除）
- 口座管理画面 / カテゴリ管理画面
- 金額表示コンポーネント（等幅数字）

## 進め方

一度に全部を作らず、**動く縦の断面から**積む。

1. BE: 取引CRUD + カレンダー集計
2. FE: カレンダー + 日別リスト + 編集シート（ここで乗り換え可能水準に到達）
3. FE/BE: 口座・カテゴリ管理
4. 仕上げ（レイアウト、Undo、連続入力）

## 想定リスク

| リスク | 対策 |
|---|---|
| 種別変更時の項目整合が漏れる | DB の CHECK 制約が最終防衛線。BE で種別ごとに不要項目を明示的に NULL 化する |
| 楽観的更新でサーバーと画面がずれる | React Query の `onMutate` / `onError` でロールバックし、確定後に再取得する |
| Basic 5DTU の同時ワーカー枯渇 | N+1 を書かない。一覧はページングし、`bootstrap` で往復を減らす |
| 取引0件からの開始で口座残高が実態と合わない | 口座管理画面で期首残高を入力できるようにする |
