# プラン: 20260812_05 — 支出マップの番号ずれと代表座標

## 対象機能・課題

「地図で見ると合っているのに、画像だとピンがズレている」

### 番号を決める式が2本あった

| | 順位に使う金額 | 上限 |
|---|---|---|
| 画像のピン（`map.ts:52-66`） | **座標がある記録だけ**の合計（`WHERE e.lat IS NOT NULL` が集計の前） | TOP 10 |
| 一覧の番号（`analytics.ts:116-133`） | **全記録**の合計（座標の有無を見ない） | TOP 30 → 画面側で座標つきに絞り上位10 |

どちらも `ORDER BY 金額 DESC` だが、**その金額が別物**。
座標を持たない記録がある店は画像側でだけ小さく評価され、順位が入れ替わる。

```
スーパーA  合計 30,000円（うち座標つき  5,000円）
スーパーB  合計 20,000円（すべて座標つき）

一覧：A=①  B=②      （30,000 > 20,000）
画像：B=①  A=②      （ 5,000 < 20,000）
```

一覧の①を確かめに画像の①を見ると、そこは別の店。座標そのものは正しいので、
📍リンクから地図で開くと合っている——報告された症状と一致する。

上限の違い（10 と 30）も同じ穴を広げる。画像側で11位以下に落ちた店は、
一覧では番号を持つのにピンが無い。

### なぜ今になって、スマホでも起きたか

「座標を持たない記録」が増えたから。**増やしたのは我々**。

| いつ | 何が座標を持たなくなったか |
|---|---|
| 一括登録の追加 | まとめ打ちは位置情報を受け取らない（設計どおり） |
| 自宅の登録 | 自宅の範囲内で付けた記録は座標を落とす |
| 8/12 の PC 対策 | 誤差500m超を `dropIfImprecise` が落とす |

PC で付けたかスマホで付けたかは関係ない。先の PC の件は、これと `AVG` の汚れが重なっていた。

### 代表座標が `AVG`

`map.ts:55-56` と `analytics.ts:121-122` が店名でまとめて緯度経度を**平均**している。

- 外れ値1件が全体を引きずる（3km ずれた1件 + 正しい10件 → 約270m ずれる）
- **同名の別店舗が中間に立つ。**「イオン」を2店舗で使えば、どちらでもない場所にピンが出る

### `system_flow.md` に書いてあることが守られていない

> 地図と一覧の番号は揃える。どちらも「位置つきを金額の多い順に上位から」で数える。
> ずれると、どの棒がどのピンか分からなくなる

**原則は書いてあるのに、実装が独立した2本のクエリになっている。**
文言を足すのではなく、**ずれられない作り**にする。

### 合意済みの前提

1. 場所集計を共有化して番号がずれない作りにする
2. 代表座標を `AVG` から変える（**直近の座標つき記録**の座標）
3. 消し残る「精度不明」の座標に対処する

## 設計の要点

### 集計を1か所に寄せる

`shared/places.ts` を新設し、`analyticsMonth` と `analyticsMap` の両方がここを読む。
`normalizeEntry` / `computeLines` / `refreshLedger` と同じ扱い。

```
PLACE_LIMIT = 30   場所別に返す上限（一覧）
MAX_PINS    = 10   地図に並べる上限。これ以上は重なって読めない

placesSelect()          共有の SELECT 文（1つだけ）
mapPlaces(places)       座標つきに絞って先頭 MAX_PINS 件。番号はこの順
```

**番号は「絞ってから数える」の1回だけ。** 地図側も `TOP 10` をやめ、
一覧と同じ 30 件を同じ順で受け取ってから絞る。こうすると
「画像側だけ11位以下に落ちる」が構造的に起きない。

### 代表座標は「直近の座標つき記録」

`AVG` をやめる。T-SQL は `GROUP BY` の中で「特定の行の値」を直接は取れないので、
**窓関数で1回だけ順位を振る**。

```sql
ROW_NUMBER() OVER (
  PARTITION BY COALESCE(e.merchant, e.place_name)
  ORDER BY CASE WHEN e.lat IS NULL THEN 1 ELSE 0 END,  -- 座標つきを先に
           e.entry_date DESC, e.id DESC                 -- その中で新しいもの
) AS rn
...
MAX(CASE WHEN rn = 1 THEN lat END) AS lat
```

`rn = 1` は「座標つきの中でいちばん新しい行。1件も無ければ座標なしの行」になる。
後者なら `lat` は NULL のままで、地図には出ない。**望む挙動そのまま。**

`OUTER APPLY` で店ごとに引き直す書き方もあるが、**Basic 5DTU では往復ではなく
索引探索が30回積む**。窓関数なら月内の行を1回なめるだけで済む。

**代表座標は同じ月の中から選ぶ。** 全期間から選べば「その月は座標なしで記録した店」にも
ピンが立ち、今の「位置つきが1件も無い月は 204」という約束が変わってしまう。
機能の意味が変わる話なので、ここでは広げない（後述の店名マスタで扱う筋）。

### 精度不明の座標

`locationsClear` は `location_accuracy > @acc` の行しか消さない（`locations.ts:132`）。
**誤差が分からない行は残る。** 値が無いことは「悪い」ことの証拠にならないため、
既定で消さないのは正しい。ただし**逃げ道が無いのが問題**。

`includeUnknown` を受け取り、明示的に指定したときだけ `location_accuracy IS NULL` も消す。
`summary` は既に件数（`unknownAccuracy`）を返しているので、
**押す前に何件消えるかは分かる**（月次締めのプレビュー→承認と同じ）。

既定は今までどおり消さない。**画面で別のボタンにして、まとめて押せないようにする。**

## 検証

```
cd 11_BE_DEPLOYMENT  && npm run build
cd 10_SITE_DEPLOYMENT && npm run typecheck && npm run build
```

`shared/places.ts` の SELECT は SQL 文の組み立てなので、**文字列として1本しか
存在しないことを確認する**（`map.ts` / `analytics.ts` に place の SELECT が残っていない）。

デプロイ後に実データで確認すること:

1. **一覧の番号と画像のピン番号が一致する。** 座標を持たない記録がある店を含む月で見る
2. 座標つきの記録が0件の月は今までどおり地図が出ない（204）
3. 同名で2か所ある店のピンが、中間ではなく**どちらかの店舗**に立つ
4. 座標を1件も持たない店は一覧に出るがピンは無い（📍も出ない）
5. 自宅ページで「誤差が分からない N件」を消せる。**消す前に件数が出る**
6. 消したあと、金額・店名・カテゴリが残っている

## 懸念事項・前提条件

1. **BE は手動デプロイ。** 直しても `npm run deploy` を実行するまで本番に出ない
2. **代表座標が「直近」なので、最後の1件が外れ値だとそれに引きずられる。**
   `AVG` より確実に良くなるが、根治ではない。根治は店名マスタ（別途検討）
3. **同名の別店舗はまだ1つのピンにまとまる。** 直近の店舗に立つので「中間の海の上」は
   無くなるが、2店舗を区別したいなら店名を分けるか、マスタが要る
4. **精度不明の消去は元に戻せない。** 既定では消さないまま、別のボタンにする
5. 窓関数を足すぶん、場所の集計がわずかに重くなる。月内の行数は数百なので
   Basic 5DTU でも問題にならない見込みだが、分析画面の応答時間を見ておく
