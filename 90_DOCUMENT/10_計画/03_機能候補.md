# 機能候補（構想メモ）

収益化検討（[SaaS 化調査](01_SaaS化調査.md)・[引き継ぎ](02_SaaS化引き継ぎ.md)）の過程で出た機能案の置き場。
**すべて未計画。** 着手するときは `development_procedure.md` に従い `91_UPDATE/01/` へ計画書を起こす。

選定の軸は収益化の構造そのまま: **継続率 → 転換率 → 単価** の順に効くものを優先し、
既存の資産（プール・一括登録・ACS メール・月次締め・スイープ基盤）の上に安く載るものを高く評価する。

作成: 2026-08-13

各案の狙いと注意:

1. **CSV 取込** — 銀行連携を持たない戦略の弱点（手入力が続かない）を、規制リスクゼロで緩和する。
   カード会社の CSV → 一括登録のプレビューに流し、店名は場所マスタと過去の記帳から候補を当てる。
   **継続率への効きが最大**とみて筆頭に置く
2. **週次サマリー** — 「先週の支出・予算の残り・プール残高」。家計簿の離脱は「開かなくなる」から
   始まるので、開く理由を毎週作る。無料枠に入れて戻ってくる導線にする
3. **ふりかえりレポート** — 締めの直後に「使いすぎたカテゴリ・プールへ退避できた額・先月比」。
   締めを作業から楽しみに変える（YNAB がリフレクション文化で継続率を稼ぐのと同じ筋）
4. **お小遣い枠** — 世帯は共有しつつ、自分のお小遣いカテゴリだけは明細を相手に見せない
   （合計のみ可視）。共有一辺倒のマネーフォワードにも共有が弱い YNAB にもない位置。
   D4（黙って見られない）の思想と一貫させること
5. **立て替え精算** — 「家族の買い物を自分のカードで立て替え → 月末に精算」を半自動で起こす
6. **買い物リスト** — 「買った」のチェックがクイック登録に落ちる。記帳アプリを「支出の後」から
   「買い物の前」へ前進させる。作り込みすぎると別プロダクトになるので入れ物は薄く（詳細は下記）
7. **目標貯金** — プールは実装済みなので追加は薄い。sinking funds として英語圏にも通じる定番
   プレミアム機能。収入と予算からの逆算〜将来シミュレーターへの発展余地あり（詳細は下記）
8. **子ロール** — 家族プランの値段を正当化する。3層化（memberships の role）が前提

### 作らないもの（再確認）

銀行連携（調査 §1）、投資・資産の**見える化競争**（MF の主戦場）、アルバムの SNS 化（P9）。

## 1・11. CSV 取込と重複 — 詳細

**CSV 取込の価値は重複の扱いでほぼ決まる。** 重複は3種類あり、対策の性質が違う。

| 種類 | 例 | 対策 |
|---|---|---|
| A. CSV 同士 | 同じ CSV を2回入れる・期間が重なる | **機械的に根絶できる**（層1） |
| B. CSV × 手入力 | 店で記帳済みのものが明細にも載る | 完全一致は不可能。**候補を出して人が決める**（層2） |
| C. 手入力同士 | 夫婦が同じ買い物を両方記帳（**既に発生中**） | 警告＋掃除（層4）。CSV を待たず先に作れる |

### 層1: 取込指紋（A を根絶）

CSV 各行から「カード＋利用日＋金額＋店名＋同日同額の連番」のハッシュを作り、
世帯ごとの一意インデックスで持つ。同じ CSV を何度入れても既取込の行は DB が弾く。
定期取引の `(recurring_rule_id, entry_date)` 一意と同じ「**DB で止める**」流儀。
「今月の分もう入れたっけ？」という不安そのものを消す。

### 層2: 取込プレビューでの突き合わせ（B）

- 鍵は**金額の完全一致＋日付±3日＋同じカード口座**。店名は当てにならない
  （手入力「イオン」vs 明細「AEONRETAIL」）ので判定の鍵にせず、表示の参考に留める
- 一致の疑いがある行はプレビューに印を付け、1行ずつ「**取り込まない（記帳済み）/ 両方残す**」を選ばせる。
  月次締めと同じ**プレビュー → 承認**の型。**自動マージは絶対にしない**
- 疑いの既定は**取り込まない側**に倒す。二重に入る事故は、入り損ねより発見しにくい
- `entry_stock`（未確定のクイック登録）も照合対象に含める
- 1つの CSV 行は最大1つの記録としか照合しない（日付が近い順に 1:1 割当）。
  「手入力2件＝明細1件」の分割照合は泥沼なので初期スコープ外。返金（マイナス行）は符号ごと照合

### 層3（発展）: 照合ビュー

CSV を「入力手段」ではなく**答え合わせの台紙**として使う。CSV 行と一致した手入力に「照合済み」が
付き、どの行とも一致しない手入力が浮かび上がる＝**二重記帳の発見器**になる。
YNAB のインポートマッチングと同じ考え方。月次締めの前の儀式として噛み合うが、実装が重いので後段。

### 層4: 手入力時の重複警告（C。#11 として独立、CSV より先）

- 保存時に「同じ日・同じ金額の記録が既にあります（◯◯さんが記帳）」を**非ブロッキング**で出す
- 「同日同額ペアの一覧」を出す掃除画面を1枚添える（既存の二重明細の後始末用）
- **正当な同額重複は普通にある**（毎朝同じ500円のコーヒー）ので、警告はしても止めない。
  DB 制約にはしない

## 6. 買い物リスト — 詳細

> **第1段（入れ物）は 2026-08-15 に実装済み。**
> `20260815_01_plan.md` / `91_UPDATE/21/20260815_updatefix_shopping.md`。
> 置き場は `dbo.shopping_items`（`schedules` は拡張しなかった）。
> 動きは[処理フロー](../system_flow.md#買い物メモ)を正とする。
> **未実装のまま残しているのは下記2つ**: 未購入分の繰り越し（「残りを今日へ移す」）と、
> 「この買い物を記帳」でクイック登録を開く橋。

**ToDo リストの操作感（サクッと追加・チェック）で、日付ごとに作る。** 2026-08-13 ユーザー合意。

- **日付に付ける。** 「8/15 の買い物」をカレンダーの日にぶら下げる。カレンダー起点の設計と
  そのまま噛み合い、新しい画面の概念が要らない。予定メモ（`schedules`）が既に日付に
  ぶら下がっているので、置き場所はその隣。テーブルを分けるか `schedules` を拡張するかは計画時に判断
- **項目は品名だけ。** 想定金額・カテゴリ・担当者・優先度は持たない。世帯で共有し、誰でも追加・チェックできる
- **チェック → 記帳の橋は「1レシート = 1記帳」を崩さない。** 品目ごとに金額を付けて台帳へ入れる
  形にすると、未実装の「明細分割」を先取りする泥沼になる。リストはメモに徹し、
  買い物後に「この買い物を記帳」でクイック登録（日付・店名入り）を開いて**合計額だけ**入れる
- **未購入分の繰り越しは自動にしない。** 「残りを今日へ移す」ボタンで明示的に行う。
  黙って翌日に湧くと予定と実績の区別が曖昧になる
- リストの中身は台帳に入らない＝集計に一切影響しない。`entries` とは接続しない
  （橋はクイック登録を開くだけ）

## 12. 予算組立 — 詳細

**「いくら配るか」を決める道具。** 現状、予算額は直接入力しかなく、初月の設定は勘で入れるしか
ない。「食費＝誰の朝昼夜おやつが日にいくら → 月でこれくらい」と**内訳から積み上げて**月額を出す。
「配る・組み換える・繰り越す」の**上流**を埋める機能で、一点集中の方向と一致する。
初期設定の挫折（3日で辞める）対策として継続率にも効き、オンボーディングの器も兼ねられる。

- **内訳はワークシートであって台帳ではない。** 行（例: 朝食 300円 × 2人 × 毎日）を積んで
  月額を算出し、既定額（`budget_categories.default_amount`）またはその月の配分へ**適用**するだけ。
  予算の実体は今まで通り `budget_allocations`。台帳の仕組みには触れない
- **算出根拠を保存する。** 適用後も内訳を残し、「なぜ食費が4.5万か」をいつでも開き直せる。
  クイック登録の `suggestion_reason`（なぜその値か分からない状態を作らない）と同じ思想
- **頻度の語彙は絞る**: 毎日 / 平日のみ / 週N回 / 月N回、×人数。柔軟にしすぎると
  表計算ソフトの再発明になる
- 内訳を持たないカテゴリは今まで通り直接入力。組立は**任意**の道具であって強制しない
- 計画時の判断事項: 月の日数（28〜31日）の扱い。既定額は想定日数で丸めるか、
  月へ適用する時点で実日数で計算し直すか

## 7. 目標貯金と簡易 FP — 詳細

**目標貯金に「逆算」と「将来設計」を足し、簡易フィナンシャルプランナーへ育てる構想。**
2026-08-13 ユーザー提案。スコープの坂道があるので3段に切り、段ごとに立ち止まる。

| 段 | 何か | 重さ |
|---|---|---|
| **第1段: 逆算** | 収入 − 予算合計 ＝ 月の積立余力。目標額 ÷ 残り月数 ＝ 必要月額。突き合わせて「間に合う / 月◯円足りない」 | **軽い。既存データだけで出せる** |
| 第2段: 複数目標の配分 | 余力を複数の目標へ優先度順に割り振る。プール実績と接続して進捗を実測 | 中 |
| 第3段: 将来シミュレーター | ライフイベント（教育費・住宅頭金・車検…）を年表に置き、残高曲線を描く | 重い。上位プラン級 |

- **#12（予算組立）と同じ「前提 → 算出 → 適用」のワークシート機構に乗せる。** 作るなら土台を共有する
- **実績が自動で重なるのが差別化。** 世の FP シミュレーターは計画を描いて終わりだが、
  ここではプール台帳が実績そのものなので、計画線に毎月の実績が勝手に重なり
  **計画とのズレが見える**。台帳アプリにしかできない部分
- シミュレーションは導出ビュー/ワークシートに徹し、**台帳には一切書かない**
  （台帳に入るのは実際のプール移動だけ）

### やらない線（先に引く）

- **利回り前提・金融商品の提案・「◯◯に投資すべき」は入れない。**
  単なる算数を超えて助言に踏み込むと**投資助言・代理業の登録問題**に触れる。
  資産運用の見える化競争（作らないもの）にも滑る
- 数十年の税制・社会保障の精密な再現はしない。**前提はすべて利用者が編集できる数字**で、
  アプリは掛け算と足し算だけを担う

### どこまで FP に近づけてよいか（2026-08-13 追記）

**FP 相談の成果物＝キャッシュフロー表は前提の掛け算と足し算**なので、第3段まで作れば
計算部分は本職とほぼ同等になる。ライフプランの試算自体は資格・登録の要る行為ではない
（規制対象は個別の金融商品の推奨・助言だけ）。よって:

| やってよい | やらない |
|---|---|
| キャッシュフロー表の算出・残高曲線 | 個別商品の推奨（「◯◯に投資すべき」） |
| **前提値のプリセット**（教育費・老後生活費などの統計平均を初期値に。編集可能＋「平均値」と明示） | 利回りの約束・断定的な将来予測 |
| 「このままだと◯年で不足」という**算数の帰結**の表示 | 個人の状況を踏まえた助言の体裁（相談応対） |

## 9. 資産タブ — 詳細

**痛みの正体は価格データの取得ではなく「口数 × 価格の計算と記帳」。** そこで2段に割る。

| 段 | 何か | ライセンス |
|---|---|---|
| **第1段** | 保有銘柄・口数を登録し、価格を入れると評価額・損益を自動計算 | **問題なし**（価格は手入力） |
| 第2段 | 価格の日次自動取得（スイープ1本追加） | **個人利用の範囲に留める**（下記） |

### 設計の線引き — 台帳を汚さない

- 保有（holdings）と価格スナップショットは**別テーブル**。`entries` は一切通さない。
  市場価格は取引なしに動くので、台帳に評価損益を書くと「残高は取引から導出する」が壊れる
- 財布合計には混ぜない。`exclude_from_totals` が既にこの事態（証券など性質の違う口座）を
  予期した設計になっている。閲覧専用の「資産」タブとして出す
- 買付・売却で実際に動いたお金だけは従来どおり台帳へ記録する
- **円建てのみ。** 米国株を入れると G1 で「絶対にやらない」と決めた多通貨の泥沼に入る

### データ源の制約（2026-08-13 確認）

- J-Quants API（JPX 公式）: 無料プランは **12週遅延**で評価額用途に使えず、実用はライト
  （月1,650円）から。かつ**「個人向けサービス」**であり、SaaS 利用者への再配信を前提にした
  商用ライセンスではない
- 投資信託の基準価額は J-Quants 対象外（投信協会・各運用会社に個別対応が要る）
- Yahoo!ファイナンス等のスクレイピングは規約違反。課金サービスの土台にできない

**よって SaaS の機能表には（データライセンスが解決するまで）載せない。**
国土地理院の逆ジオ（調査 §5）と同種の「利用規約の壁」で、こちらのほうが重い。
第1段を自家用に作り、気に入れば「手動更新前提のライト資産タブ」としてプレミアム同梱を再検討する。

## 10. 今日は何の日・簡易天気 — 詳細

記帳したついでに「今の外の状況がちょっと分かる」彩り。単体では課金理由にならないが、
**毎日開く画面に小さな楽しみを置く**のは継続率の下支えになり、コストがほぼゼロ。

- **今日は何の日**: 静的データセットで足りる。API 不要
- **天気**: 第一候補は**気象庁の公開 JSON**（API キー不要）。「接続文字列と API キーを
  どこにも保持しない」方針を崩さない点で国土地理院と同枠だが、**SLA なし・規約の商用可否は
  展開前に要確認**（調査 §5 の国土地理院と同じ扱い）
- 位置の扱いは既存方針に従う: 市区町村レベルの粗い位置で足りるので、精密座標は使わない。
  自宅判定で座標を捨てる設計とも矛盾しない
- **置き場所は記帳の動線を妨げない位置**（カレンダー下部など）。広告の置き場所と同じ原則
  （記帳中の画面には出さない）を適用する。
  **器は用意済み**: カレンダー下部の折り畳みブロック（`components/Collapsible.tsx`）に
  そのまま載る。閉じていれば中身を描かないので、外部 API を叩く機能ほど相性がよい
- 発展の余地: 記帳時に天気を添えて保存すれば、いずれ「雨の日の支出」のような分析の彩りになる。
  ただしスコープが膨らむので当面は**表示のみ**
