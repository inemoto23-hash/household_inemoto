# 20260812 アップデート予定（明細をあとから定期取引に変える）

- **計画書**: `91_UPDATE/01/20260812_02_plan.md`（承認済み）
- **ユーザー手動手順**: なし（DB マイグレーションも不要）

## やること

定期取引を作れる場所が「新しく記録するとき」と「設定の定期タブ」の2つしかない。
既に付けた明細を見て「これ毎月だ」と気付いても、そこからは作れず、
同じ内容を設定タブで手入力し直すことになっていた。

**取引の編集シートに「定期取引にする」を出す。**

| 対象 | 内容 |
|---|---|
| DB | 変更なし |
| BE | `domain/recurrence.ts`（`occurrenceOnOrAfter`）、`functions/recurring.ts`（create / update） |
| FE | `lib/recurrence.ts`、`EntryForm.tsx`、`CalendarPage.tsx` |
| 文書 | `system_flow.md` / `91_UPDATE/21/` |

API の追加はない。既存の `POST /api/recurring`（`skipFirst: true`）をそのまま使う。

## 先に潰す危険：過去に遡って自動記帳される

`recurringCreate` は次回予定日が**過去日でも構わず保存する**。
`recurringSweep` は `next_date <= 今日` を拾い、62日以内なら記帳する。

> 今日 8/12。6/20 の家賃 8,000円を「毎月20日」に変える
> → `next_date` = 7/20（23日前）→ その晩のタイマーが **7/20 付けの明細を勝手に作る**

口座残高と過去月の予算が後から動く。今回の機能を入れると日常的に踏むので、先に止める。

## 決めたこと

- 次回予定日は**今日以降の最初の該当日**から。過去分は記帳しない
- **`start_date` は明細の日付のまま。動かすのは `next_date` だけ**
  （「毎月20日」が明細から素直に導ける。週次の間隔は開始週を基準に数えるので起点を動かすとずれる）
- 元の明細は**そのまま残す**。規則とは紐付けない（新規記録から定期にするときと同じ振る舞い）
- 「定期にする」は**編集中の変更を保存してから**規則を作る
- 返金は対象外（`EntryForm` と `ruleInputSchema` の両方で既に閉じている）

## 注意する点

- **止めるのは1か所に寄せる。** `domain/recurrence.ts` に `occurrenceOnOrAfter` を1本足し、
  `recurringCreate` と `recurringUpdate` の**両方**に適用する。
  片方だけ直すと「作ると遡らないのに、直すと遡る」という罠になる
- **`recurringSweep` には手を入れない。** あちらはタイマーが止まっていた規則を拾い直すためのもので、
  目的が違う
- **画面の「次は」も同じ基準にする。** `previewNext` は開始日から数えているため、
  起点が過去だと過去の日付を「次は」として出してしまう。
  `lib/recurrence.ts` の冒頭が「サーバーと必ず揃えること」と明記しているとおりに揃える
- **規則づくりに失敗しても明細の保存は巻き戻さない。**
  新規記録側と同じ判断（「記録は残っているほうが常に良い」）
- **変換したことを必ず見せる。** 「定期取引に登録しました（次は9月20日）」を出す。
  次回予定日はサーバーの返り値を使い、画面で計算し直さない

## 今回やらないこと

- 同じ明細を2回変換したときの重複防止（紐付けない判断の帰結。設定タブで気付ける形にする）
- 「この規則はこの明細から作った」という履歴の保持
