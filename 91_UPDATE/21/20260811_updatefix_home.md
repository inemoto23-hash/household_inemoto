## やったこと

クレジットカードの履歴は、店ではなく自宅でまとめて付けることが多い。
そこに位置情報を添えると次の2つが起きていた。

- 支出マップに自宅がピンとして並ぶ（実際に使った場所ではない）
- 店名の候補が「自宅の近所で過去に使った店」から出て、当たらない

自宅を1つ登録し、その範囲で記録したものは**位置情報を持たせない**ようにした。

## データベース

`20_DATABASE/migrations/012_home.sql`（適用済み）。

`dbo.households` に `home_lat` / `home_lng` / `home_radius_m` を追加。
テーブルは増やしていない。1世帯に1つだけの値のため。

半径は既定50m。屋内では GPS が数十m ずれるので、画面から 50 / 100 / 200m を選べる。

### 判断したこと

**座標を保存しないことで解決する。** 「保存した上で地図側で除外する」形にすると、
除外条件が地図・分析・店名候補の3か所に散らばり、いずれ抜ける。
入口で持たせなければ、下流は今のままで正しく動く。実際、支出マップ側の
コードは1行も変えていない。

**判定は BE で行う。** 画面側でも判定するが、それは表示のためだけ。
`normalizeEntry` が種別ごとの項目を必ず落とすのと同じ考え方で、
**画面が座標を送ってきても BE が捨てる。**

**矩形で絞ってから距離で確定する。** 過去分を消すとき、緯度経度の矩形だけで
判定すると角が半径の約1.4倍まで入る（実測 70.7m / 半径50m）。
矩形は候補を減らすためだけに使い、距離で確定する。

**消すのは位置だけ。** 金額・店名・カテゴリは残す。
「自宅で付けた」ことと「何に使ったか」は別の話。

**解除しても過去分は戻らない。** どれを外したか記録していないため。
解除の説明文にそう書いてある。

## 検証したこと

### 距離の計算

| 内容 | 結果 |
|---|---|
| 緯度0.001度 | 111.2m（理論値どおり） |
| 経度0.001度（緯度36） | 90.0m（理論値どおり） |
| 同一地点 | 0m |
| 東京駅→渋谷駅 | 6,455m（実距離と整合） |
| 未登録 / 位置なし | 常に「自宅ではない」 |
| 矩形の辺 | 北辺・東辺とも 50.0m（半径を包む） |
| 矩形の角 | 70.7m ＝ 半径の1.41倍（距離での確定が必要なことを確認） |

### 実データでの絞り込み

自宅をマクドナルドの座標に仮置きし、矩形の候補が期待どおりになることを SQL で確認。

| 対象 | 距離 | 判定 |
|---|---|---|
| マクドナルド | 0m | 範囲内 |
| 31アイスクリーム | 35m | 範囲内 |
| セキ | 541m | 範囲外 |
| Povo | 671m | 範囲外 |

矩形での候補は2件で、距離で確定した結果と一致した。
