# 明細をあとから定期取引に変える

## Context

いまは定期取引を作れる場所が2つしかない。**新しく記録するとき**（記録シートの「定期取引にする」）と、
**設定 → 定期タブ**（一から入力）。既に付けた明細を見て「これ毎月だ」と気付いても、
そこからは作れない。同じ内容を設定タブで手入力し直すことになる。

この導線は意図的に塞いであった。`EntryForm.fromEntry` の
「既存の記録を後から定期にする導線は用意しない。定期の追加は設定タブから行う」がそれで、
[完了記録](../../../Desktop/CLAUDE%20PROJECT/家計簿アプリ/91_UPDATE/21/20260811_updatefix_recurring.md) にも
同じ結論だけが残っている。**理由は書かれていない**（当時の計画書は別内容で上書き済み）。
今回それを開ける。塞いだ理由が残っていない以上、開けた理由のほうを記録に残す。

### 先に潰すべき危険：過去に遡って自動記帳される

`recurringCreate` は次回予定日を `skipFirst ? nextOccurrence(開始日) : firstOccurrence()` で決めるだけで、
**それが過去日でも構わず保存する**。`recurringSweep` は `next_date <= 今日` の規則を拾い、
62日以内なら記帳するので、こうなる。

> 今日 8/12。6/20 の家賃 8,000円を「毎月20日」に変える
> → next_date = 7/20（23日前）→ その晩のタイマーが **7/20 付けの明細を勝手に作る**

口座残高と過去月の予算が後から動く。これは今回の機能を入れると日常的に踏むので、
**先に止める**。同じ穴は既存の2経路（過去日付の記録から定期にする／設定タブで過去の開始日を入れる）にも
開いているので、入口を1か所に寄せて塞ぐ。

### 合意済みの前提（Q&A で確定）

1. 次回予定日は**今日以降の最初の該当日**から。過去分は記帳しない
2. 元の明細は**そのまま残す**（規則とは紐付けない＝新規記録から定期にするときと同じ振る舞い）
3. 「定期にする」は**編集中の変更を保存してから**規則を作る

## 設計の要点

### 規則の起点は明細の日付、次回だけ未来へ押し出す

`start_date` は明細の日付のままにする。「毎月20日」という規則が明細から素直に導けるし、
毎週の間隔（隔週など）は開始週を基準に数えるため、起点を today にすると周期がずれる。
**動かすのは `next_date` だけ。**

### 止めるのは1か所

`domain/recurrence.ts` に純粋関数をひとつ足す。

```ts
/** date を含めて、それ以降で最初の該当日 */
export function occurrenceOnOrAfter(r: Recurrence, date: string): string | null
```

中身は `nextOccurrence(r, addDays(date, -1))`。`nextOccurrence` は `after` を含まない仕様なので
1日戻すだけで「その日を含む」に変わる。月次は添字計算で O(1)、週次も最大 `intervalN` 回で、
ループで1回ずつ進める実装より速い。

`recurringCreate` と `recurringUpdate` の両方で、算出した `next` が `todayJst()` より前なら
これで引き直す。**片方だけ直すと「作ると遡らないのに、直すと遡る」という罠になる。**

`recurringSweep` の追いつき処理には**手を入れない**。あちらはタイマーが止まっていた規則を
拾い直すためのもので、目的が違う。

### 画面の「次はいつ」も同じ基準で出す

`RecurrenceFields` は `previewNext(value, startDate, startDate)` で開始日の翌日から数えている。
起点が過去だと**過去の日付を「次は」として表示してしまう**。
`lib/recurrence.ts` の冒頭が「実際に記帳される日を決めるのはサーバー。ここは確認用だが必ず揃えること」と
明記しているとおり、サーバーと同じく「開始日と今日の遅いほう」から数える。
1行の変更で、新規記録・変換・設定タブの3経路すべてが揃う。

**`update` の流れ** — PATCH で明細を保存 → `form.recurrence` があれば
`toPayload(form)` + `toRecurrencePayload(form.recurrence, form.entryDate)` + `skipFirst: true` を
`POST /api/recurring`。新規作成側（`create`）と同じ形なので、送る組み立ては共通の考え方のまま。

規則づくりに失敗しても**明細の保存は巻き戻さない**。`create` 側と同じ判断
（「記録は残っているほうが常に良い」）。失敗はトーストで伝える。

**変換したことを必ず見せる。** 「定期取引に登録しました（次は9月20日）」を出す。
黙って閉じると、規則ができたのか分からない。次回予定日は `POST` の返り値の `nextDate` を使う
（画面で計算し直さない）。トーストは削除の取り消しと同じ位置・同じ見た目にし、
`CalendarPage` 内の小さな部品として両方から使う。

`refund` は対象外。`EntryForm` が既に `value.kind !== 'refund'` で出し分けており、
`ruleInputSchema` も refund を受け付けないので、画面とサーバーの両方で閉じている。

## 検証

```
cd 11_BE_DEPLOYMENT && npm run build
cd 10_SITE_DEPLOYMENT && npm run typecheck && npm run build
```

`domain/recurrence.ts` は純粋関数なので、ビルド後の `dist` に対して直接確かめる
（一括登録のときと同じやり方）。

- `occurrenceOnOrAfter` が**その日を含む**こと（該当日ちょうどを渡したらその日が返る）
- 月末の丸めが `nextOccurrence` と一致すること（1/31 → 2/28 → 3/31 に戻る）
- 終了日を過ぎたら `null`
- 過去の開始日 + `skipFirst` で、次回が今日以降になること

画面（実 DB が要らない範囲）:
- 過去日の明細を開き「定期取引にする」→ 「次は」が**未来の日付**になっている
- 収入・振替でも出る。**返金では出ない**
- 新規記録シートの表示が今までと変わらない

デプロイ後に実データで確認すること:
1. 3か月前の明細を毎月の定期にする → 設定タブの次回予定日が未来。**翌朝、過去日付の明細が湧いていない**
2. 金額を直してから「定期にする」→ 明細も規則も直した額になっている
3. 変換後、元の明細がカレンダーに残っている（消えていない・重複していない）

## 懸念点

1. **同じ明細を2回変換すると規則が2本できる。** 紐付けない判断（合意事項2）の帰結で、
   画面からは検知できない。トーストから設定タブへ誘導して気付ける形にする。
   実害が出るようなら `entries.recurring_rule_id` を使う設計に変える
2. **`recurringUpdate` にも手を入れる。** 今回の依頼の範囲を少し超えるが、
   create だけ直すと経路で挙動が割れる。変更は同じ2行
3. **既存の「次は」表示が変わる。** 過去の開始日で作った規則の表示が未来の日付に変わる。
   これは表示が実態に合っていなかったのを直すもので、退行ではない
