# SaaS 化 — 方針決定と引き継ぎ

[SaaS 化調査](01_SaaS化調査.md)（以下「調査」）のレビューを受けた**方針の決定事項**と、
次に作業するエージェントへの**引き継ぎ**。調査本文と重複する説明は書かない。根拠は調査の該当節を参照。

作成: 2026-08-13（レビューと同日）

## 1. 決定事項

1. **プロジェクトは白紙に戻さない。** 撤退コストが低く（身内運用は月1,000円前後）、
   初期の作業は身内利用にも効くため（調査 [§10 R7](01_SaaS化調査.md#r7-総合判断)）
2. **収益化を「目的」に据えない。** 着地点は「月1〜3万円＋自家用＋技術資産」
   （調査 [§8 位置づけ](01_SaaS化調査.md#位置づけ)）。時給換算で合わない前提を受け入れる
3. **投資はゲートで刻む**（下記 §2）。ゲートを通過するまで、次段の投資（課金・法務・ストア・英語圏）に着手しない
4. **調査ドキュメント内の施策は全部クリアしていく前提**（ユーザー決定、2026-08-13）。
   ただし「いつやるか」はゲートが決める

## 2. ゲート定義と現在地

| ゲート | 通過条件 | 通過したら着手してよいもの | 状態 |
|---|---|---|---|
| **G0: 身内** | 配偶者を含む2人以上で3ヶ月回る | 着手順①②③（3層化・通貨/TZ・i18n の器） | **← 現在地。2人運用を確認（2026-08-13）。3ヶ月の継続実測中** |
| **G1: 無料公開** | 登録100人 / 4週継続率20%以上 | 課金（⑤）・法務（⑧） | 未達 |
| **G2: 課金開始** | 有料10契約 / 月次解約率10%未満 | ストア（⑨）・英語圏（⑩）・上位プラン | 未達 |

**やめる基準:** 無料公開から6ヶ月で G1 に届かなければ、収益化は畳んで身内運用へ戻す。

番号（①〜⑩）は調査 [§9 着手順](01_SaaS化調査.md#9-着手順) の表に対応する。
着手順①②は「磨きこみ中に実施」とあるが、**G0 通過（配偶者登録＋3ヶ月運用）が先**。
記録がまだ少ない今のうちに①②をやる利点と、実測ゼロのまま投資する欠点のトレードオフは
ユーザーが判断する（§5 未決事項）。

## 3. 次のエージェントへの作業指示

### いますぐ（G0 の間にやること）

1. **磨きこみの継続。** 現在の主戦場は UI の実測調整とバグ出し。新機能よりも継続利用の障害を潰す
2. ~~配偶者の登録~~ **済（2026-08-13 確認）。** メンバー画面で確定状態（oid 紐付け済み）を確認。
   G0 の3ヶ月カウントはここから
3. **月次エクスポートの実装**（再構築計画 Phase 4 の未実装分）。
   課金以前に、自分の台帳データのバックアップとして必要（調査 [§10 R4](01_SaaS化調査.md#r4-自動テストが無いまま課金しない)）
4. ~~`domain/` の単体テスト整備~~ **済（2026-08-13）。** Vitest 導入、9ファイル・86テスト。
   ゼロサム（`buildTransferPair` に一本化）・繰越（`computeCloseLines` へ抽出）・
   `ck_entries_shape` の鏡像（`normalizeEntry`）を固定。
   詳細は `91_UPDATE/21/20260813_updatefix_betest.md`。
   **残**: DB モックが要る統合テスト（世帯分離まわり）は課金前の前提条件のまま。
   Phase B の抽出は次回 BE デプロイに同乗＋締めプレビューのスモーク
5. **管理者アカウントの防御。** Global Administrator を持つアカウントが唯一の砦で、
   ここを取られると MI・共有キー禁止などの構成の堅さは全部無意味になる。
   **パスキーまたは MFA の強制**（ユーザー手動作業）。安価で効果が最大の対策なので最優先。
   **手順を `19_ユーザー作業.md` §7 に用意済み（2026-08-13）** — MSA 本体の2段階認証＋
   Entra セキュリティの既定値群の有効化の2層。実施待ち
6. **依存パッケージの監査。** リポジトリが GitHub へ push されていないため Dependabot が効いていない。
   push するまでの間は `npm audit`（FE・BE 両方）を定期実行する
   - **2026-08-13 実施:** BE は 0件。FE は react-router 6.x に moderate 2件
     （オープンリダイレクト GHSA-wrjc-x8rr-h8h6 / SSR ハイドレーション注入 GHSA-337j-9hxr-rhxg）。
     **SSR 不使用＋全 `navigate()` が内部値のみで、現コードに攻撃経路は無い。**
     修正版は v7.17.1 以降のみ（6.x に修正は来ない）ため、**react-router 6→7 の移行を
     別件の軽い計画として起票する**（急がないが、6.x に留まる限り警告は消えない）

### 着手順①②③を始めるとき

- **必ず `development_procedure.md` に従い、Plan モードで計画書を起こして承認を得る**
  （`91_UPDATE/01/` へ保存）。この引き継ぎ文書は計画書の代わりにならない
- 計画に**必ず含めること**:
  - D1〜D9（3層化）と G1・G2（通貨・タイムゾーン）を**1つの計画・1回のマイグレーション群**（`018` 以降）にまとめる（調査 §9）
  - **External ID 移行の布石**を同じ計画に入れる（下記 §4。調査 [§10 R3](01_SaaS化調査.md#r3-external-id-への移行で既存ユーザーの紐付けが切れる--着手順の技術的欠落)）
  - 調査 [§2 残る論点](01_SaaS化調査.md#残る論点)（招待権限・所属世帯数上限・プラン変更時の世帯の扱い）への回答をユーザーに確認してから設計を固める

### 課金（⑤）を始める前の前提条件（G1 通過後）

調査 [§10 R4](01_SaaS化調査.md#r4-自動テストが無いまま課金しない)・[R6](01_SaaS化調査.md#r6-法務課金まわりの不足項目) を計画に落とす:

- 回帰テスト（締め・組み換え・定期記帳）、BE デプロイの CI 化、検証環境
- 特商法2022改正の最終確認画面（6項目表示・解約の簡便性）を課金画面の設計要件に
- Stripe の現行料率（Billing 込み）確認、督促（dunning）設定
- 商標調査（J-PlatPat）、漏えい時対応手順、サービス終了手順の規約化
- **世帯分離の認可テスト。** 3層化で `memberships` 参照へ書き換えた判定ロジックが
  多テナント漏洩の最大のリスク箇所になる。「別世帯のリソース ID を混ぜたリクエストが必ず弾かれる」
  ことをテストで固定してから課金を開始する
- **運営者向け管理画面（2026-08-13 追加）。** セルフサインアップを開けた瞬間から、
  ユーザー登録情報・世帯・契約状態の照会、アカウントの無効化、削除請求への対応が要る。
  **最小構成（照会・無効化）は G1（無料公開）の時点で必要**、課金管理（プラン・請求状態）は⑤と同時。
  設計線: **D4 と同じく、運営者からも台帳の中身（金額・明細）は見えない作りにする。**
  見えるのはアカウント・世帯・契約の状態だけ。サポートで中身が要る場合は本人の同意を都度取る
- **利用規約・プライバシーポリシーは課金前ではなく「無料公開前」が期限**（着手順⑧のとおり）。
  位置情報を扱うため無料でも必須。特商法表記のみ課金開始時でよい
- **セキュリティレビューの実施。** 課金開始前に世帯分離・認可まわりを集中的に見る
  （`/security-review` の利用可）。クラウドの銘柄（Azure vs AWS）は突破されやすさを決めない。
  リスクは自分側の設定とアプリの認可バグに集中しており、移行は検討しない（2026-08-13 決定）

## 4. 検証済みの技術的事実（2026-08-13 時点のスナップショット）

次のエージェントが再調査しなくてよいよう、レビューで確認した事実を残す。
**時間が経っていたらコードで再確認すること**（SSOT はソースコード）。

### 認証まわり — External ID 移行の要点

- 現在は **workforce テナント**（B2B ゲスト招待）。CIAM ではない
- `11_BE_DEPLOYMENT/src/shared/auth.ts` は `TENANT_ID` 1つから JWKS / issuer を組み立てる
  **単一テナント前提**。issuer は v1/v2 の2本を許容するが同一テナント
- External ID は**別テナント**＝ issuer も既存ユーザーの `oid` も変わる。
  そのまま切り替えると oid 検索が全員外れ、**403 で全員ロックアウト**
- 移行手順（無停止）:
  1. `auth.ts` を issuer / JWKS を配列で受ける形に一般化し、新旧テナントを並行受理
  2. 既存ユーザーの `provider_user_id` を NULL に戻す（UPDATE 1本）
  3. 初回サインインの**メール照合による自動紐付け**（既存機構、`auth.ts`）で新 oid が入る
- 要事前検証: CIAM の Google サインインで `email` クレームに素のアドレスが入るか
  （現行の `#EXT#` 復元ロジックとはクレーム形が変わる）
- `uq_users_email` は `(household_id, email)` 複合。D1 の `users` グローバル化で
  **email のグローバル一意性を別途設計**する必要がある

### 現況

- 利用者: **2人**（オーナー＋配偶者。2026-08-13 にメンバー画面で確定状態を確認。
  `seed_master.sql` はオーナー1行のみだが、配偶者は招待フローで追加済み＝シードと実態は異なる）
- Google フェデレーション: 未設定（Google Cloud Console 側の作業待ち）。現状は MSA でサインイン
- 自動テスト: **0本**（`test` スクリプトも依存も無い）
- デプロイ: FE のみ CI（SWA）。BE・DB マイグレーションは手動
- バックアップ: Azure SQL PITR 7日のみ。エクスポート未実装
- `schema_migrations` に 006〜010 の適用記録が欠落（スキーマ自体は適用済み）

### 外部情報（2026-08-13 に確認）

- 英語圏競合: YNAB 年 $109。下位価格帯は **Actual Budget（無料 OSS）/ Goodbudget（年 $80・世帯共有あり）/
  EveryDollar（無料枠）/ Simplifi（年 $36）** で既に埋まっている。差別化は価格でなく機能の形で
  （調査 [§10 R5](01_SaaS化調査.md#r5-英語圏は安い-ynab-代替の枠が既に埋まっている--7-の補正)）
- 特商法2022年改正: 最終確認画面の6項目表示義務・解約手段は申込みと同程度に簡便であること
- Paddle（MoR）は 5% + $0.50。月額 $5.99 だと実質13% → **英語圏は年額主体で設計**
