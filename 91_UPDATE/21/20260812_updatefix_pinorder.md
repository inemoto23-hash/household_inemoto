## 1. 前回の修正が中途半端だった

`20260812_05` で「地図と一覧が同じ SQL を読む」ようにしたが、**同じクエリを2回実行する**
形にしただけだった。リストと画像は別リクエストで、それぞれが順位を計算していた。

| 残っていた穴 | 何が起きるか |
|---|---|
| `ORDER BY 2 DESC` に決め手が無い | 同額の店があると、実行ごとに並びが入れ替わりうる |
| 画像だけキャッシュが長い | 一覧30秒 / 画像1時間。古い画像と新しい一覧が並ぶ |

**番号を2回数えている限り、食い違う余地は消えない。**

「リロードしても直らない」は切り分けにならなかった。画像は JS の `fetch()` で取るため、
**スマホの再読み込みでは HTTP キャッシュ（`max-age=3600`）を迂回しない。**
どちらが主因かを詰めるより、両方あり得ない作りにした。

## 2. 画像は順位を決めない

`functions/map.ts` から**DB アクセスを消した**（`getPool` の import も無い）。
受け取った地点を受け取った順に描くだけ。

```
GET /api/analytics/{ym}/map?w=&h=&p=35.123456,139.123456;35.234567,139.234567
```

**番号は並びの位置そのもの。** ラベルを別に受け取らないので、
「番号と座標がずれて渡る」という事故が起こせない。
Azure Maps のラベルが ASCII しか解釈できない制約も、これで自動的に守られる。

`p` が無い・空なら **204**。400 にすると、デプロイの前後で古い画面がエラー表示になる。
204 なら地図が静かに消えるだけで済む。

上限 `MAX_PINS`（10）で切り捨てるのは**安全弁**であって、どれを載せるかの判断ではない。
緯度 -90..90 / 経度 -180..180 の範囲検査を入れ、外れていれば 400。

## 3. 番号を数えるのは画面の1か所だけ

`AnalyticsPage` が `mapPins` を1本作り、**一覧の番号もこれ、画像に渡すのもこれ**にした。

```tsx
const mapPins  = places.filter(座標あり).slice(0, MAX_PINS);
const pinNumbers = new Map(mapPins.map((p, i) => [p.name, i + 1]));
<SpendingMap pins={mapPins} />
```

`shared/places.ts` からは「地図に出す場所を選ぶ」関数を削除した。
残しておくと、また2か所で数えることになる。

## 4. キャッシュが中身で決まるようにした

地点を queryKey と URL の両方に入れた。**ピンが変われば URL が変わる**ので、
古い画像が出てくる経路が無い。逆に中身が同じなら取り直さない。

このため `Cache-Control: private, max-age=3600` を**外す必要がなくなった**
（Azure Maps の呼び出し回数も増えない）。`refreshLedger` に `['map']` を足す必要もない。

## 5. 一覧の並びを安定させた

`ORDER BY amount DESC, name`。同額のときの決め手が無いと、
**一覧そのものが取り直すたびに入れ替わりうる**。画像は一覧に従うので、ここが要になる。
