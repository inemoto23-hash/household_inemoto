# プラン: 20260812_06 — 番号を1回だけ数える

## 対象機能・課題

支出マップで「①と③が逆」。📍リンクで開くと正しい位置なのに、画像の番号が一覧と合わない。

### 前回の修正が中途半端だった

`20260812_05` で「地図と一覧が同じ SQL を読む」ようにしたが、**同じクエリを2回実行する**
形にしただけだった。リストと画像は別リクエストで、**それぞれが順位を計算している**。

そのため次の余地が残った。

| 残った穴 | 何が起きるか |
|---|---|
| `ORDER BY 2 DESC` に決め手が無い | 同額の店があると、実行ごとに並びが入れ替わりうる |
| 画像だけキャッシュが長い | 一覧は30秒、画像は1時間（BE の `Cache-Control` も1時間）。古い画像と新しい一覧が並ぶ |

**番号を2回数えている限り、食い違う余地は消えない。**

なお「リロードしても直らない」は原因の切り分けにならない。画像は JS の `fetch()` で
取っているため、**スマホの再読み込みでは HTTP キャッシュ（`max-age=3600`）を迂回しない**。

## 実装方針

### 画像は順位を決めない

**1回だけ数えて、その結果を画像に渡す。**

| | 今 | あるべき形 |
|---|---|---|
| 一覧 | 集計して番号を振る | 集計して番号を振る（**1回だけ**） |
| 画像 | **もう一度集計して番号を振る** | 番号と座標を**受け取って描くだけ** |

画像は自分では何も決めないので、**一覧と食い違うことが原理的に起きない**。
同額でも、キャッシュが古くても、順位を決め直さないのでずれない。

### 番号は「並びの位置」そのものにする

ピンは順番に並べて渡し、**BE は受け取った順に 1, 2, 3… を振る**。
ラベルを別途送らないので、「番号と座標がずれて渡る」という事故が起こせない。

Azure Maps のラベルは ASCII しか解釈できない（非 ASCII は `%E5%AE%B6` とそのまま描かれる）。
番号を位置から作れば、この制約も自動的に守られる。

### キャッシュは URL に含める（内容で決まるようにする）

座標を URL に載せると、**ピンが変われば URL が変わる**。

```
GET /api/analytics/{ym}/map?w=&h=&p=35.123456,139.123456;35.234567,139.234567
```

記録を足せば一覧の順位が変わり、`p` が変わり、別の画像になる。
**古い画像が出てくる経路が無くなる**ので、長期キャッシュを外す必要がない
（Azure Maps の呼び出し回数も増えない）。

react-query のキーにも `p` を入れる。`refreshLedger` に `['map']` を足す必要もなくなる
——キーが内容で決まるため、放っておいても正しいものに切り替わる。

### 一覧側の並びも安定させる

`ORDER BY 2 DESC` に決め手が無いままだと、**一覧そのものが取り直すたびに入れ替わりうる**。
`ORDER BY amount DESC, name` にする。画像は一覧に従うので、ここが安定すれば全体が安定する。

### 受け取った座標の扱い

- 上限 `MAX_PINS`（10）で**切り捨てる**。これは順位の判断ではなく安全弁
- 緯度 -90..90 / 経度 -180..180 の範囲検査。外れていれば 400
- `p` が無い・空なら **204**（地図を出さない）。400 にすると、
  デプロイの前後で古い画面がエラー表示になる。204 なら静かに地図が消えるだけで済む

座標は利用者自身の世帯のものが返ってきたものを送り返すだけなので、
**新しく漏れる情報は無い**。任意の座標を描けてしまうが、描けるのは自分向けの画像1枚で、
認証済みの利用者が Azure Maps の呼び出しを1回使うだけ。

## 懸念事項・前提条件

1. **デプロイ順は BE → FE。** 逆にすると、新しい FE が `p` を送っても
   古い BE が無視して自前で順位を決める。BE を先に出せば、古い FE は `p` を送らず
   204 になり、地図が数分消えるだけで済む
2. **順位を決める場所が FE に移る。** 集計は今までどおり BE（`analytics`）が行い、
   FE は「その結果から上位を切り出す」だけ。導出は1か所のまま
3. **URL が長くなる。** 10地点で約250文字。上限には遠い
4. ピンの位置そのもの（同名の別店舗、外れ値）は**今回直らない**。店名マスタの領分
5. 実 DB での確認は引き続きデプロイ後になる
