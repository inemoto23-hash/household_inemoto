## やること

支出マップの「①と③が逆」。前回の修正は「同じクエリを2回実行する」形にしただけで、
**リストと画像がそれぞれ順位を計算している**構造が残っていた。

| 対象 | 内容 |
|---|---|
| DB | 変更なし |
| BE | `shared/places.ts`、`functions/map.ts`（**DB アクセスを無くす**） |
| FE | `features/analytics/AnalyticsPage.tsx` |
| 文書 | `system_flow.md` / `91_UPDATE/21/` |

## 決めたこと

- **画像は順位を決めない。** 一覧が決めた並びを受け取って描くだけにする
- **番号は並びの位置そのもの。** ラベルを別送しないので、番号と座標がずれて渡る事故が起こせない
- **座標を URL に載せる。** ピンが変われば URL が変わる＝古い画像が出てくる経路が消える。
  長期キャッシュを外す必要がなくなり、Azure Maps の呼び出しも増えない
- `ORDER BY amount DESC, name` — 同額でも一覧の並びが毎回同じになる
- `p` が無い・空なら **204**。400 にするとデプロイ前後で古い画面がエラーになる

## 注意する点

- **デプロイは BE が先。** 逆にすると、新しい FE が `p` を送っても古い BE が無視して
  自前で順位を決める＝症状が変わらないまま「直したのに直らない」に見える。
  BE を先に出せば、古い FE は `p` を送らず 204 になり、地図が数分消えるだけで済む
- **`map.ts` から DB アクセスを消しきること。** `getPool` の import が残っていたら、
  順位を決める道が残っているということ
- 受け取った座標は `MAX_PINS`（10）で切り捨てる。**これは順位の判断ではなく安全弁**
- 緯度経度の範囲検査を入れる。範囲外は 400
- Azure Maps のラベルは ASCII のみ。番号を位置から作れば自動的に守られる
